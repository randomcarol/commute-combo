# 房补通勤组合搜索 H5 设计文档

- 日期：2026-08-01
- 状态：已过方案评审，待进入实现规划
- 项目代号：Commute Combo

## 1. 背景与问题

面向大厂校招/社招租房场景，用户在判断某套房是否落在房补范围内时，常常需要手动在不同地图软件中反复尝试不同的分段组合，例如步行、骑行、地铁的不同拼接方式，并比较不同地图软件给出的时间差异。

现有地图产品的问题不在于不能导航，而在于不会自动替用户完成以下工作：

- 穷举合法的分段测距组合
- 比较高德、百度、腾讯三家地图结果
- 自动发现最短且合规的通勤测距方案
- 告诉用户后续应该用哪张图去复核和截图

因此，本项目的核心价值不是“查询通勤时间”，而是“自动搜索合规的最优测距方案”。

## 2. 产品定位

`Commute Combo` 是一个 H5 小工具，帮助用户输入公司地点、房源地点和房补规则后，自动搜索步行、骑行、地铁的合法分段组合，并比较高德、百度、腾讯三家地图的时间结果，输出最短的合规方案。

一句话表述：

> 这不是普通导航工具，而是一个房补通勤组合搜索器。

## 3. 目标与非目标

### 3.1 MVP 目标

- 支持用户输入公司地址与房源地址
- 支持用户配置或选择房补规则模板
- 支持公司别名、楼栋别名、小区多个门口的候选点输入
- 自动搜索步行、骑行、地铁的高价值分段模板
- 比较高德、百度、腾讯三家地图的结果
- 输出最短合规方案与若干备选方案
- 提供路线明细与推荐复核地图

### 3.2 非目标

- 不做账号体系
- 不做租房平台房源抓取
- 不做电动车、公交、打车等模式
- 不做自动截图或自动提交房补申请
- 不做全国特殊职场完整政策库
- 不做无限制任意段数的组合搜索

## 4. 目标用户

核心用户：

- 在大厂附近租房、对房补政策敏感的校招生和初级职场人
- 正在筛选边界房源，希望“卡进”房补范围的用户

典型使用场景：

- 看中一套离公司直线较远的房子，想知道是否能通过骑行加地铁等方式压进规则边界
- 不想手动在三款地图里反复试错
- 想在看房前快速判断某个片区是否存在合规方案

## 5. 用户规则抽象

MVP 需要支持配置化规则，不把规则硬编码成单一公司策略。

首版默认支持的规则表达：

- 纯步行：总时长 <= 30 分钟
- 纯骑行：总时长 <= 20 分钟
- 纯地铁：总时长 <= 20 分钟
- 分段组合：各段时长加总后 <= 20 分钟

后续规则扩展能力：

- 支持不同公司的模板预设
- 支持特殊职场单独配置阈值
- 支持限定可用模式组合，例如只允许“骑行 + 地铁”

## 6. 关键产品假设

- 三家地图的结果存在可比较但不完全一致的时间差
- 用户更关心“最短合规方案”而不是“绝对真实的唯一方案”
- 用户仍需要回到地图软件自行复核与截图，因此本产品承担的是“搜索与决策”角色，而不是“官方凭证”角色
- 高频价值来自减少人工试错，而不是替代地图软件本身

## 7. 产品方案

### 7.1 用户输入

用户输入以下信息：

- 公司地点
- 房源地点
- 房补规则模板或自定义规则
- 公司候选别名
- 房源候选门口

### 7.2 系统输出

系统返回：

- 最优合规方案
- 备选方案列表
- 每个方案的分段方式与总时长
- 每段的起终点、中转站和地图来源
- 是否合规
- 与阈值的差距
- 建议去哪个地图进一步复核截图

### 7.3 页面结构

#### 页面 1：搜索页

- 公司地址输入
- 房源地址输入
- 规则模板选择
- 公司别名管理
- 小区门口管理
- “开始搜索最优通勤组合”按钮

#### 页面 2：结果列表页

- 顶部摘要区：最优合规方案、总时长、合规状态
- 方案榜单：按照总时长升序展示
- 每条卡片显示：
  - 总时长
  - 分段方式
  - 来源地图
  - 是否合规
  - 距离阈值还差多少

#### 页面 3：方案详情页

- 分段明细
- 每段耗时
- 中转站信息
- 推荐复核地图
- 截图建议顺序

#### 地图可视化浮层

- 用不同颜色展示步行、骑行、地铁段
- 让用户理解该方案是如何拼接出来的

## 8. 搜索与计算逻辑

### 8.1 总体思路

系统不是直接查询“房源到公司”的单条路线，而是：

1. 将输入地址转成候选坐标集合
2. 生成高价值的中转点候选
3. 枚举固定模板的分段组合
4. 对每个组合请求高德、百度、腾讯的路线结果
5. 将返回数据标准化后计算总时长
6. 按规则判定是否合规并排序

### 8.2 地址标准化

候选点集合由两部分组成：

- 公司侧：
  - 公司主名称
  - 楼栋别名
  - 园区入口
- 房源侧：
  - 小区主名称
  - 小区各门口

系统将这些输入解析成多个可尝试的起终点组合。

### 8.3 中转点候选

首版只生成高价值中转点：

- 公司附近地铁站
- 房源附近地铁站

不对全城任意 POI 做无限搜索，避免成本和搜索空间失控。

### 8.4 分段模板

MVP 固定支持以下模板：

- 步行
- 骑行
- 地铁
- 步行 -> 地铁
- 骑行 -> 地铁
- 步行 -> 地铁 -> 步行
- 骑行 -> 地铁 -> 步行

这组模板覆盖了绝大多数用户实际会尝试的房补测距方式，也能解释“系统在自动做原本用户手动试的事情”。

### 8.5 多地图调用

每个模板会对三家地图分别调用：

- 高德：步行 / 骑行 / 公交-地铁
- 百度：步行 / 骑行 / 公交-地铁
- 腾讯：步行 / 骑行 / 公交-地铁

对返回结果统一抽象为：

- provider
- mode
- duration
- distance
- segments
- transit metadata

### 8.6 排序与判定

主排序键：

- 是否合规
- 总时长升序

辅助信息：

- 来自哪家地图
- 哪种分段模板
- 每段耗时
- 离规则阈值的余量

结果分层：

- 合规最优
- 合规备选
- 接近边界
- 不合规

## 9. 技术架构

### 9.1 前端

建议：

- React H5
- 地图展示 SDK 仅用于可视化，不承担核心计算

职责：

- 采集地址与规则输入
- 展示方案榜单与方案详情
- 可视化路线

### 9.2 后端

建议：

- Node.js BFF

职责：

- 托管三家地图 API key
- 调用地图开放平台接口
- 做签名、限流、缓存与重试
- 标准化三家地图返回结构
- 执行组合搜索与排序逻辑

### 9.3 数据存储

MVP 只需轻量存储：

- 查询记录
- 公司规则模板
- 公司别名/楼栋名

可使用：

- SQLite
- Supabase

## 10. 为什么不用页面爬取

不采用直接爬高德/百度/腾讯页面或 App 的方式，原因如下：

- 页面结构不稳定
- 合规性差
- 难以自动化批量比较
- 前端无法安全管理调用逻辑
- 面试展示时可维护性和工程合理性较弱

因此，MVP 采用官方开放平台 API + 自有搜索引擎的方式实现。

## 11. 成功标准

MVP 成功的判断标准：

- 用户输入一组公司与房源地址后，系统能在可接受时间内返回候选方案
- 方案结果中能明确指出最优合规路径
- 用户无需自己手动在三款地图里逐项试错
- 结果具备可解释性，用户知道每段是如何拼接的

## 12. 第二阶段方向

第二阶段可扩展：

- 申报截图辅助
- 公司规则模板库
- 热门片区推荐
- 地址收藏与批量比较
- 特殊职场规则覆盖

## 13. 风险与限制

- 三家地图接口在字段、时长口径、可用模式上可能存在差异
- 地铁方案通常会夹带步行接驳，需要统一到“分段可解释”的结果格式
- API 调用成本会随组合数量快速上升，需要通过模板限制和缓存控制成本
- 最终公司是否认可该截图仍取决于官方测距口径，本产品不提供申报保证

## 14. MVP 结论

首版应聚焦于证明一个核心价值：

> 不依赖用户手动试错，自动搜索三家地图中的最短合规分段通勤方案。

如果该价值成立，再扩展到截图申报辅助和房源筛选场景。
