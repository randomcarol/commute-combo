# 产品 Spec

## 1. 项目名称

房补通勤组合搜索器 `Commute Combo`

## 2. 问题定义

目标用户在判断某个房源是否落入公司房补范围时，往往不是直接看“房源到公司”的单条导航，而是会手动做这些动作：

- 试不同地图
- 试不同门口
- 试不同楼栋别名
- 试骑行、步行、地铁和分段组合
- 试不同测距时段

现有地图能给出单条路线，但不会主动替用户比较这些高价值组合。

## 3. 用户痛点

### 3.1 显性痛点

- 房补边界房源需要反复试错
- 手动切换高德 / 百度 / 腾讯很费时间
- 用户不知道该先试哪个门口、哪个楼栋别名
- 分段截图流程繁琐

### 3.2 隐性痛点

- 用户很难证明“这已经是能找到的更优路线之一”
- 用户即使搜到了可行路线，也不清楚要截图哪几段
- 用户容易因为一次搜索结果不理想就放弃某个房源

## 4. 核心价值主张

不是做一个普通导航工具，而是做一个：

> 自动比较高价值通勤组合，并推荐最短合规方案的房补测距辅助工具。

## 5. 目标用户

- 大厂校招生、应届生、初级职场人
- 对房补政策敏感的租房用户
- 正在筛选房补边界房源的用户

## 6. 当前 MVP 范围

### 6.1 已纳入

- 公司地点输入
- 租房小区输入
- 高德候选地点下拉
- 高德主算路
- 步行 / 骑行 / 混合三段方案
- 同名门口 / 楼栋别名比较
- 结果排序与截图清单

### 6.2 暂不纳入

- 账号体系
- 房源抓取
- 地图账号登录态复用
- 自动截图
- 自动提交房补
- 特殊职场规则库
- 无限组合穷举

## 7. 产品成功标准（commute-r1.0）

对于一次作者自测输入，系统至少要做到：

1. 给出可理解的起终点识别结果
2. 给出若干条可复核的候选通勤方案
3. 当 `北门 / 西塔 / 栋` 这类同名别名更快时，能把它推荐出来
4. 明确告诉测试者每一段怎么截图并回到地图 App 复核

合法模板统一为：`walk`、`bike`、地图端到端 `subway`、`bike->subway->bike`。系统找到普通路线不代表产品成功；只有系统规则合规、地图复核一致且截图可用，才计入“有效测距完成”。

## 8. 当前产品与理想目标的差距

### 8.1 已经解决的部分

- 不再只看原始起终点
- 不再把无关附近 POI 随意混入结果
- 可以比较同名派生别名

### 8.2 仍未完全解决的部分

- 还没有做更大规模别名候选池
- 还没有形成城市 / 园区级别的门口与楼栋知识库
- 还没有从真实样本中学习哪些别名最有效
- 还没有做到“你在高德手搜的所有有效技巧都能被系统稳定复现”
