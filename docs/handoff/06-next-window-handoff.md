# Next Window Handoff

## 项目一句话

房补通勤组合搜索器 `Commute Combo`，目标是帮用户把房源和公司之间的通勤方案自动拆解、比较、排序，尽量找出最短且合规的房补测距方案。

## 目前产品目标

- 输入房源和公司
- 自动识别地点候选
- 比较高价值别名，例如 `中海雅园` / `中海雅园北门`
- 只保留房补规则允许的方式
- 给出最短、最可信、可截图复核的方案

## 已确认的规则

- 允许：`walk`、`bike`、`subway`、`bike->subway->bike`
- 不允许：公交混入、`walk->subway->walk`、`bike->subway->walk`
- 地铁方案必须显示站点区间
- 结果排序优先级：
  1. 合规
  2. 段数更少
  3. 总时长更短
  4. 同名别名更优先比较

统一规则版本为 `commute-r1.0`。旧文档中出现的 `walk->subway->walk`、`bike->subway->walk` 不再作为合法模板；综合公交只以地图端到端 `subway` 结果进入判断。

## 迭代过程

1. 先做了 demo 版 H5。
2. 再接入实时地图，优先高德。
3. 修正了地点识别，不再乱换成无关 POI。
4. 修正了地铁识别，避免把公交线路当地铁。
5. 收紧结果展示，只保留有业务价值的候选。
6. 现在发现一个核心问题：当前 live 版还没有做“高德超时一点点时自动切百度/腾讯”的 fallback。

## 当前已知现状

- 高德主算路已接通
- 候选下拉可用
- live / demo 曾经混过，后面已经尽量收紧到实时地图结果
- 现在仍然需要补的是：
  - AMap 轻微超时后的百度 / 腾讯 fallback
  - 更快的搜索停止策略
  - 更稳定的结果排序和解释文案

## 下一步要做

1. 加自动 fallback
   - 先高德
   - 如果结果接近超时但没命中，再试百度 / 腾讯
2. 限制搜索爆炸
   - 同一类方案只保留最优少量结果
   - 超时严重的直接丢弃
3. 强化地铁展示
   - 必须显示从哪站到哪站
   - 必须显示分段耗时
4. 清理旧模板
   - 统一只保留当前有效路线类型

## 给新窗口的起始句

“继续做房补通勤组合搜索器，先补 AMap 轻微超时后自动切百度/腾讯的 fallback，并保持结果只展示合规且最短的方案。”
