# 设计与用户流

## 1. 页面结构

当前页面分成三块：

- 顶部 Hero：说明产品定位
- 搜索条件区：输入公司地点、租房小区和房补阈值
- 结果与详情区：展示最优方案、备选方案、截图清单

## 2. 交互流程

### 2.1 标准流程

1. 用户输入公司地点
2. 用户输入租房小区
3. 前端调用 `/api/suggest` 拉取高德候选
4. 用户点击或继续保留输入文本
5. 前端调用 `/api/search`
6. 后端返回结果列表和元信息
7. 前端渲染：
   - 数据来源
   - 最优方案
   - 备选方案
   - 方案详情
   - 截图清单

### 2.2 失败兜底流程

如果前端访问不到 `/api/search`，会自动切到 demo 数据模式，用于保底展示页面结构。但这个模式不能作为真实测距依据。

## 3. 结果展示原则

### 3.1 结果卡片

每条卡片至少要有：

- 来源地图
- 路线模板
- 总时长
- 阈值
- 合规状态
- 起终点摘要

### 3.2 方案详情

详情区会显示：

- 每一段的起点和终点
- 每段耗时
- 地铁段上下车站
- 截图顺序

### 3.3 策略说明

如果当前最优结果来自同名门口 / 楼栋别名比较，页面会额外提示：

- 已比较同名门口 / 楼栋别名
- 当前推荐的更快起终点是什么

这样用户不会误以为系统“偷偷改了输入”。

## 4. 当前设计取舍

### 4.1 为什么前端只保留两个主输入框

因为用户不应该自己先懂：

- 哪个门更近
- 哪个楼栋别名更快
- 哪个站点应该拿来做分段

这些应该是系统搜索逻辑的一部分，而不是让用户做前置配置。

### 4.2 为什么还保留房补阈值输入

`commute-r1.0` 默认规则是：

- 步行 30 分钟
- 骑行 / 地铁 20 分钟
- 骑行 → 地铁 → 骑行 20 分钟

只有 `walk`、`bike`、地图端到端 `subway`、`bike->subway->bike` 可判为合法。余量 0–2 分钟显示“临界合规·待复核”，不能使用“可直接申报”文案。

但这个工具以后要支持不同公司规则，因此阈值输入现在保留是合理的。

## 5. 当前设计的不足

- 还没有显示“所有候选点比较表”
- 还没有用地图可视化方式展示各段路线
- 还没有单独显示“原始点 vs 北门 / 西塔”的完整比较清单
- 还没有对真实用户的理解成本做可用性测试

## 6. 下一步推荐设计增强

### 6.1 高优先级

- 增加“候选比较表”
- 明确展示：
  - 原始点
  - 北门 / 南门 / 西塔 / 东塔
  - 各自耗时
  - 被推荐原因

### 6.2 中优先级

- 给每个结果增加“为什么推荐”
- 给混合路线增加更清晰的三段时间汇总

### 6.3 低优先级

- 增加路线小地图
- 增加分享链接
