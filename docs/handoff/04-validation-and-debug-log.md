# 校验与调试总结

## 1. 调试背景

本项目在 2026-08-01 到 2026-08-02 期间经历了多轮从 demo 版到 live 版的修正，核心问题集中在：

- live key 生效链路
- 地图返回结构兼容
- 起终点识别
- 门口 / 楼栋候选策略
- 展示文案与真实搜索行为不一致

## 2. 关键问题与结论

### 2.1 服务没跑在 live 模式

问题：

- 只启动了 `python3 backend/server.py`
- 没在同一个终端进程里带上 `COMMUTE_PROVIDER_MODE=live`

结论：

- 后端默认是 `mock`
- 前端请求失败时还会自动退回 demo 数据

### 2.2 高德接口结构兼容问题

问题：

- 骑行接口存在 v5 / legacy 两种返回结构
- 地铁 `segments` 有时是对象，不是数组

结论：

- 需要兼容不同返回结构
- 不能假设字段一定存在

### 2.3 起终点被替换成无关附近 POI

问题：

- 曾经存在“根据附近 POI 自动找门口”的逻辑
- 会把输入点替换成看起来不相关的地点

表现：

- 出现用户没输入过的楼名、门名、门市名

结论：

- 这种逻辑会破坏用户信任
- 已改成只允许“同名派生别名”

### 2.4 过度保守导致没有真正解决痛点

问题：

- 为避免乱换起终点，曾把策略收得过死
- 精确起终点一旦合规，就不再比较同名门口 / 楼栋别名

表现：

- 工具结果反而比用户直接在高德手搜更差

结论：

- 这是错误的产品策略
- 正确做法应该是：
  - 不使用无关附近 POI
  - 但必须比较同名高价值别名

### 2.5 排序逻辑冲突

问题：

- 如果一味把 alias 降权，会导致更短的 `北门 / 西塔` 方案上不来
- 如果一味把总时长放在段数前面，又会让三段路线压过直达路线

结论：

- 当前合理排序是：
  1. 合规优先
  2. 段数更少优先
  3. 总时长更短优先
  4. 完全同分时才更偏向精确点

## 3. 关键修复

### 3.1 候选比较策略修复

已改为：

- 精确点与同名 alias 一起比较
- alias 更快时允许上位
- 不再因为精确点已合规就提前停止

### 3.2 展示解释修复

已增加：

- 当推荐结果来自门口 / 楼栋别名时，页面会解释“已比较同名门口 / 楼栋别名”

### 3.3 云试用能力修复

已增加：

- `COMMUTE_SERVER_HOST`
- `COMMUTE_SERVER_PORT`
- `/healthz`

## 4. 当前验证状态

### 4.1 已执行

- 后端单元测试
- 排序回归测试
- provider 行为测试
- server 行为测试
- 前端展示测试
- Python 语法检查
- Node 语法检查

### 4.2 当前结论

- 代码层处于“可试用”状态
- 产品层还需要作者完成同一批地址的人工 / 工具配对样本进一步校正

## 5. 当前已知遗留问题

### 5.1 真实路线仍可能不如用户手动高德技巧

原因：

- 现在只比较少量高价值别名
- 还没引入更大的门口 / 楼栋知识池

### 5.2 地图配额与并发限制仍是风险

尤其是高德 `10021` 限流时，会直接影响体验。

### 5.3 还没有完整候选比较表

用户仍然无法看到：

- 原始点耗时
- 北门耗时
- 西塔耗时
- 为什么最终推荐当前方案

这会影响产品的解释性。
