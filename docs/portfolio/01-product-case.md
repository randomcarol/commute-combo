# 产品案例：把房补测距从“反复试路线”变成可复盘搜索

## 事实

- 当前产品是原生前端 + Python 标准库后端的技术原型，主要接入高德。
- 已能比较原始地点、同名门口 / 楼栋别名、地铁出入口和少量合法组合。
- 当前研究者与测试者均为项目作者本人，没有可声称的真实用户量、访谈样本、上线数据或 A/B 结果。

## 问题与机会

房补边界地址需要在地图 App 中反复改写起终点、切换方式、尝试站点并截图。地图擅长单次导航，租房平台擅长房源筛选，但两者都没有把“按公司规则穷举高价值组合并形成复核证据”作为主流程。

## 产品判断（假设）

高价值不是提供更多路线，而是：用透明的候选策略降低漏试，用统一规则避免错误合规，用地图复核闭环沉淀可解释证据。

## 方案

1. 候选层：原始 POI、同名门口 / 楼栋别名、地铁出入口。
2. 组合层：`commute-r1.0` 白名单内的四类模板。
3. 判断层：分开记录“有路线”“系统合规”“有效测距完成”。
4. 解释层：推荐原因、节省分钟数、排除原因、复核步骤。
5. 证据层：request_id 串联结果展示、复核和反馈；CASE 编号用于配对实验。

## 当前实验结果

尚未产生首批 20 个匿名地址样本，因此不填写成功率、提升幅度或用户结论。数据看板在样本少于 20 时固定标注“样本量较小，仅用于探索性验证”。

## 待验证问题

- 别名策略能否在不同地址上稳定改善 Top-1，而不是偶然命中？
- 端到端地铁与分段拼接的偏差是否可接受？
- 推荐解释能否让作者更快完成地图复核和截图？
- 规则白名单是否与目标公司的实际材料要求一致？

## 项目边界

不做综合租房平台、不抓取房源、不自动提交房补、不把系统判断包装成公司最终认定。
